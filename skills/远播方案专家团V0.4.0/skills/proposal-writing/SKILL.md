# Proposal Writing · 正式方案主笔方法

目标：把已经确认的设计写成 **正式客户方案**，而不是“像方案的大纲”，也不是把内部材料换个说法直接抄出去。

## 0. Clientization Pass（先于正文）
先建立“来源信息 → 客户表达”的边界：
- 正式公开名称：可直接使用；
- 用户提供但属于内部称呼/人名/会议/排期：只用于理解，不直接外显；
- 有明确正式名称：用正式名称替换；
- 无正式名称：改为功能性中性表述，或省略来源只表达建设要求；
- 需确认：未确认前不写。

例：
- “回应书记诉求：加强生涯与学科融合” → “项目将进一步加强生涯教育与学科学习的衔接”。
- “乔老师课程” → 有正式课程名则用正式名；无正式名时写“学校现有生涯课程/相关主题课程”，并向 Leader 标记正式名待确认。
- “按王总要求增加展示区” → 正文只写展示区为什么需要、服务什么场景，不写“王总要求”。

**所有 `clientization_guard.internal_only_terms[].raw` 在客户稿中默认零出现。**

## 1. 结构由项目生成
不预设固定七章。先回答：客户按什么顺序最容易理解“为什么做 → 做成什么 → 学生/教师怎么用 → 空间与资源如何承载 → 怎么运行和验收”。

**详略布局（大纲阶段必须完成，硬规则）**：定大纲时为每一章同时确定 `depth`（detailed / standard / brief）与**篇幅预算**（预计字数或占比）：
- **详写（detailed）**：本项目的差异化核心章——顶层理念落地、特色课程/育人体系、特色空间场景，通常 2-4 章，占全文主要篇幅；
- **标准（standard）**：支撑性章节；
- **简写（brief）**：实施计划、保障机制、运行管理等常规章——写清责任与节奏即可，**不展开铺陈**；
- **禁止全篇均匀用力**：所有章节 depth 相同、篇幅平均分配 = 大纲不通过，必须先分出主次再写正文。

## 2. Section Card
每章写前内部形成（depth 直接沿用大纲阶段的详略规划，不得临时拉平）：
```yaml
section:
purpose:
reader_questions: []
must_include: []
presentation:
  overview: prose | table | list | mixed
  detail: prose | table | list | mixed
depth: brief | standard | detailed   # 来自大纲详略布局
budget: <预计字数>                    # 来自大纲篇幅预算
```
写完后逐项检查 reader_questions 是否已回答；并核对实际篇幅是否符合 budget（detailed 章不得写薄，brief 章不得写胀）。Section Card 不向客户展示。

## 3. Content Form Router
### 表格
多个对象 × 多个共同维度，且读者需要横向比较。
### 自然段
背景、原因、判断、设计理念、学生学习过程、空间为什么这样设计、项目价值。
### 列表
真正的步骤、任务、规则、能力项、资源类别。

规则：如果读者需要比较，用表格；如果需要理解原因，用文字。表格后只补新判断，不复述表格。

## 4. 完整度门禁
高度怀疑 `OUTLINE_LIKE_OUTPUT`：
- 多个二/三级标题只有一句话；
- 核心章节只有 bullet 没有完整论述；
- 课程/空间只有“定位+主要内容”两三句；
- 关键设计逻辑被一个表格完全替代；
- 项目复杂度很高，但每章信息密度极低。

对 detailed 核心章节通常至少包含：明确判断 + 完整解释 + 真实活动/机制 + 必要结构化概览。

## 5. 客户语言
- 成熟学校：写“承接、深化、协同、延展”，慎写“补短板、亟待改变”。
- 学校文化自然融入，不设“校训转译”小节。
- 内部讨论词改为客户可接受表达，不交代“谁要求、谁提出、内部怎么讨论”。
- 设备/价格有独立清单时，正文重点写能力与配置逻辑。
- 预期成果不写成已实现事实。

## 6. 政策写法
`教育变化 → 学校已有基础 → 新的建设机会/需要 → 本项目响应`。

**筛选纪律（硬规则）**：从 EVIDENCE_BRIEF 的政策信号中**只选 2-3 条与项目建设动作最相关**的写入正文，写成论证性段落；**禁止把调研到的所有政策以“政策汇总表”或逐条罗列形式铺陈进客户稿**——未入选政策只留在内部 Brief，不进正文。

## 7. Proper Noun Audit（专有名词审阅）
终稿前逐项检查：
- 人名/领导称呼；
- “X老师课程/XX系统/那套方案”等内部昵称；
- 文件名、附件名、版本名；
- 内部部门简称、会议名、排期名；
- 其他学校/项目名称。

问题不是“这个词真不真实”，而是“客户是否应该以这种方式看到它”。无法证明为正式客户名称时，默认改写或删除。

## 8. Senior Editing
1. 删除无信息句；
2. 合并正文/表格/总结重复；
3. 删除无依据战略升华；
4. 减少“不是A而是B”“从A到B”、机械对仗、连续排比；
5. 避免每章同一种三段式/结尾；
6. 减少抽象名词堆积；
7. 保留真正解释项目的概念与结构。

## 9. 返修规则
Writer 只能声明“我已按 R1/R2 修改”，不能声明“QA 已通过”。返修稿必须回到 quality-reviewer 做 closure review。

## 10. 正文最终自检
- 每章是否有明确任务？
- 哪些句子只是在“显得专业”？
- 哪些内容换学校名仍成立？
- 表格是否帮助比较？
- clientization_guard 的 raw 内部词是否 0 出现？
- 是否还有人名/内部文件名/内部来源痕迹？
- 读者能否看出学生/教师到底怎么用这个项目？

## 11. 精美 Word 排版规范（交付定型，禁止裸草稿交付）
内容稿 leak_scan 通过后，由 Leader 用受控 python-docx 脚本产出**精排版** `.docx`（不要直接拿草稿交付，草稿排版简陋）。

**内置模板要素**
- 封面页：客户交流版——项目全名 + 客户学校 + 日期；**不得出现“内部资料/报价/公司派人”等字样**。
- 字体：**全文统一微软雅黑**（标题加粗、正文常规，不再使用宋体/思源宋体）；正文**段首缩进 2 字符**。
- 配色：低饱和蓝绿为主色，砖红/莫兰迪为点缀，避免大红大绿；页眉页脚用同色系浅灰。
- 标题层级：一级 18–20pt、二级 14–16pt、三级 12–13pt，带浅色底纹或左侧色条。
- 表格：统一边框、表头浅蓝绿底白字、斑马纹（隔行浅灰）、单元格内边距适中，覆盖所有结构化信息。
- 图示：保留双螺旋/空间布局等 PNG，统一图题（微软雅黑小五、居中、图序自动）。
- 页眉页脚：页眉左学校/项目名简写，页脚居中页码；封面无页码。
- 输出文件名带 `_精排版` 后缀，与原草稿区分。
- 排版**只改视觉、不改文案**；排完**重跑一次 leak_scan** 确认无新增泄漏。

**实现说明（给 Leader）**
- 用 `python-docx` 重建文档（设定 Normal 样式字体/字号/缩进 → 封面 Section → 逐章写入标题与正文（检测缩进）→ 表格统一套用 `_table_style_oriented` 样式 → add_picture 插图并加图题）→ 保存。
- 优先使用 WorkBuddy 托管解释器（路径形如 `%USERPROFILE%\.workbuddy\binaries\python\versions\<ver>\python.exe`，macOS/Linux 为 `~/.workbuddy/binaries/python/versions/<ver>/bin/python`）或项目 venv；若缺包先在隔离环境安装 `python-docx`，不污染用户环境。
