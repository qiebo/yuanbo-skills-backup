# Grill-me 需求澄清指南

本指南固化"先问清需求再执行"的澄清方法，供阶段 0 强制澄清及后续阶段缺口补问使用。

## 1. 适用判定

凡涉及"做 / 改 / 建 / 跑 / 配置"等动作型任务，默认进入澄清流程。

可不必追问的例外：
- 纯阅读、检索、解释类（Ask 模式）；
- 用户已给出明确、充分指令的简单任务（无歧义、无隐含假设）。

## 2. 核心规则

1. **一次只问一个问题**，不批量抛出多个问题。
2. 根据用户回答**持续追问、逐层收敛**，直到消除歧义。
3. 仅当信心达到 **95% 以上**（完全理解真实需求、目标与全部所需信息）时，才动手执行。
4. 宁可多问几轮，也不在理解不充分时盲目开工。

## 3. 追问策略

按"从方向到细节、从硬约束到软偏好"的顺序逐层收敛：

1. **先定方向**：交付给谁、什么文类、用来做什么（决策/申报/汇报/采购）——这一层错了全盘皆错，最先问。
2. **再定硬约束**：预算口径、价格来源、交付格式、必须出现/禁止出现的内容。
3. **再定形态偏好**：整段叙述 vs 结构化用表、篇幅量级、是否配图、封面标签。
4. **最后定边界与分工**：哪些内容由外部权威清单提供、哪些仅概念引用、协作方是谁。

每一问只锁定一个点；用户答完再决定下一问，不要预设答案。

## 4. 话术示例

- 锁定方向："这份方案是给学校领导决策用，还是用于向上级部门申报？"
- 锁定硬约束："预算总额以哪份清单为准？是主清单约 65 万，还是含装修/大屏的口径？"
- 锁定形态："课程与空间部分，您希望整段叙述，还是叙述 + 汇总表并存？"
- 锁定边界："设备命名与价格以同事的配置清单为准，还是本方案需要自行展开明细？"

## 5. 95% 把握判定标准

满足以下全部条件，方可视为澄清完毕：

- 交付对象与文类明确，无第二种合理理解；
- 全部硬约束（预算口径、价格来源、格式、红线）有明确答案或已登记为待确认；
- 全部隐含假设（形态、篇幅、配图、封面）已与用户核对；
- 外部权威清单（若有）的边界与分工已确认；
- 再提一个问题，也想不出会改变方案方向/预算/真实性的疑问点。

任一条件不满足，继续追问。

## 6. 阶段 0 强制澄清 vs 后续阶段缺漏才问

| 时机 | 强度 | 说明 |
|---|---|---|
| 阶段 0（执行计划前） | 强制、从头澄清 | 按第 3 节逐层收敛至 95% 把握 |
| 阶段 1 及以后 | 缺漏才问 | 仅当发现新增歧义/信息缺口时，就缺口点一次一问补充澄清，不强制每阶段从头追问 |

## 7. 与节点确认机制的配合

- 本指南管"**开始执行前问清需求**"（输入端，SKILL.md §2.4）；
- 节点确认机制管"**产出节点交付后请确认**"（输出端，SKILL.md §2.5）；
- 两者职责独立：先澄清需求再动手，产出节点再请确认，形成"问清 → 做对 → 确认"的闭环。
